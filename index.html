About

I build backend systems, the parts that stay up at 3am when everything else is asleep. Most of my career has lived in Java and Spring Boot, writing services that other systems and other people depend on: insurance verification workflows where the numbers directly affect what a patient owes, a title and settlement platform moving high-volume transactions between lenders and agents, an enterprise SaaS product used across 90+ countries.

I like problems with real constraints: a legacy system that can't be rewritten over a weekend, two systems that were never designed to talk to each other, a query that's slower than it should be under real load. The interesting part of backend work usually isn't the framework, it's the decisions around it. Where a service boundary goes. What happens when a call fails halfway through. How you migrate a production system without a maintenance window.

Along the way I've also spent time on a fintech engagement, building payment and compliance microservices for a client platform. That's one project in a career that's mostly been SaaS, insurance, and enterprise systems, and I describe it that way rather than rounding up to "fintech engineer."

Engineering case studies

Patterns and problems I've worked on, described generally. No proprietary implementation details or confidential company information.

Modernization

Modernizing a legacy application without a rewrite

An enterprise title and settlement platform had a JSF monolith that had grown past the point where a full rewrite was realistic: too much embedded business logic, too much risk in a big-bang cutover. The approach was to peel it apart incrementally. New functionality was built as standalone Spring Boot microservices, with traffic moved over piece by piece while the legacy application kept serving everything not yet migrated.

The hard part wasn't the new code. It was defining service boundaries that matched the business domain, keeping both systems consistent during the transition, and sequencing the migration so each step removed a real architectural bottleneck instead of sitting half-finished. It meaningfully improved system availability during peak transaction periods.

Strangler-style migrationSpring Boot Service boundariesLegacy JSF
Reliability

Event-driven reliability under real transaction load

Async payment processing fails in specific, well-understood ways: a consumer crashes mid-batch, a downstream service is briefly unavailable, a message gets processed twice. On a payments platform, I used Kafka and Spring WebFlux to decouple the processing stages so the system stayed responsive under load and a failure in one stage didn't cascade. That meant retries, idempotent handlers, and clear ownership boundaries per service rather than one big transactional blob.

Observability is part of the design, not an afterthought. You need to see where a message is stuck before you can explain why. This is the same pattern behind Notifly, a personal project built specifically around resilient event pipelines.

KafkaSpring WebFlux IdempotencyAsync processing
Performance

Finding the real bottleneck before fixing it

Most performance problems I've traced come down to a few causes: an N+1 query hiding behind an ORM, a batch read pattern that doesn't match the database's strengths, or a connection pool sized for a different load than the one it's actually serving. On an enterprise SaaS platform, profiling first, rather than guessing, turned up N+1 issues and a MongoDB batching pattern that needed restructuring. Fixing those delivered a consistent 15% performance improvement.

On a payments platform with defined SLAs, the same discipline applied to PostgreSQL: real query plans before touching indexes, connection pool tuning, and Redis caching in front of read-heavy paths, all measured against the SLA rather than a vague sense of "faster."

Query profilingN+1 fixes Index designRedis caching
Integration

An integration layer for systems that don't agree

A common shape of problem: a dozen external systems, each with its own schema, none of which match your internal domain model, and no realistic way to make them agree. The pattern that holds up is a normalized internal domain model, a transformation layer that maps each external schema onto it, and per-system adapters that own the translation and the failure handling for that one integration. That includes cases where the external system can't accept a structured API call at all, so the adapter falls back to generating a document instead.

This keeps the core domain logic ignorant of any particular external system, so adding a new integration doesn't mean touching code that has nothing to do with it. Kept intentionally conceptual here: it describes a pattern I've applied in a regulated, integration-heavy domain, not the specifics of any one confidential system.

How I work

Understand the problem first

Architecture should follow business requirements and real constraints, not the other way around. I'd rather spend an extra day understanding the problem than a week redoing a design built on the wrong assumptions.

Design for failure

Retries, idempotency, transactions, and observability aren't add-ons. They're part of the design from the start. A system that only works when nothing goes wrong isn't finished.

Keep systems understandable

I prefer clear service boundaries and maintainable designs over cleverness. Complexity should earn its place, not arrive by default.

Measure, don't assume

Query plans, real metrics, and production constraints beat intuition about what's "probably" slow. I try to have evidence before I change something for performance.

AI as an accelerator, not a substitute

I use tools like Claude Code, Cursor, ChatGPT, and Gemini, along with MCP-based workflows, to move faster through implementation and exploration. Architecture, trade-offs, and final decisions are still mine. AI speeds up the work; it doesn't replace the judgment behind it.
