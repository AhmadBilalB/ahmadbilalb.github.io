About

I build backend systems — the parts that stay up at 3am when everything else is asleep. Most of my career has lived in Java and Spring Boot, writing services that move data reliably: managing contacts and permissions, keeping a SaaS product's state consistent across a few hundred thousand users, or processing financial workflows where a dropped message actually matters.

I like problems with real constraints — a legacy system that can't be rewritten over a weekend, a query that's slower than it should be, two systems that were never designed to talk to each other. The interesting part of backend work usually isn't the framework; it's the decisions around it: where a service boundary goes, what happens when a call fails halfway through, how you migrate a production system without a maintenance window.

I've worked inside enterprise title and settlement platforms, SaaS products used across dozens of countries, and — for a shorter stretch — fintech-adjacent transaction and reporting systems. I try to be precise about what I've actually built versus what I've only touched, and I'd rather under-claim than round up.

Engineering case studies

Patterns and problems I've worked on, described generally — no proprietary implementation details or confidential company information.

Modernization

Modernizing a legacy application without a rewrite

A long-running JSF application had grown past the point where a full rewrite was realistic — too much embedded business logic, too much risk in a big-bang cutover. The approach was a Strangler Fig migration: new functionality built as Spring Boot microservices behind a routing layer, with traffic moved over feature by feature while the legacy application kept serving everything not yet migrated.

The hard part wasn't the new code — it was defining service boundaries that matched the business domain, keeping both systems consistent during the transition, and sequencing the migration so each step shipped value instead of sitting half-finished. The lesson that stuck: migration strategy is a design problem in its own right, not just an implementation detail.

Strangler Fig Spring Boot Service boundaries Legacy JSF
Reliability

Event-driven reliability with Kafka

Notification and messaging systems fail in specific, well-known ways: a consumer crashes mid-batch, a downstream service is briefly unavailable, a message gets processed twice. Rather than treating these as edge cases, I design for them as the normal case — consumer groups for horizontal scaling, retry policies with backoff, dead-letter queues for messages that can't be processed automatically, and idempotent handlers so a redelivered message doesn't double-charge or double-notify anyone.

Observability is part of the design, not an afterthought — you need to see where a message is stuck before you can explain why. This pattern is the backbone of Notifly, a personal project built around exactly this problem.

Kafka Consumer groups Dead-letter queues Idempotency
Performance

Diagnosing and fixing database performance

Most performance problems I've traced trace back to the same few causes: a missing or wrong index, a query doing more work than the access pattern needs, or a connection pool sized for a different load than the one it's actually serving. My default approach is to look at the actual query plan before changing anything — guessing at indexes without one usually makes things worse, not better.

Where read load is the bottleneck, Redis caching in front of PostgreSQL is often the more honest fix than throwing more indexes at a write-heavy table. I measure before and after against a defined SLA rather than treating "faster" as the goal in itself.

PostgreSQL Query plans Indexing Redis caching
Integration

An integration layer for systems that don't agree

A common shape of problem: several external systems each with their own schema, none of which match your internal domain model, and no realistic way to make them agree. The pattern that holds up is a normalized internal domain model, a transformation layer that maps each external schema onto it, and per-system adapters that own the translation and the failure handling for that one integration.

This keeps the core domain logic ignorant of any particular external system, so adding a new integration doesn't mean touching code that has nothing to do with it. This case study is kept intentionally conceptual — it describes a pattern I've applied in different contexts, not the specifics of any one confidential system.

How I work

Understand the problem first

Architecture should follow business requirements and real constraints — not the other way around. I'd rather spend an extra day understanding the problem than a week redoing a design built on the wrong assumptions.

Design for failure

Retries, idempotency, transactions, and observability aren't add-ons — they're part of the design from the start. A system that only works when nothing goes wrong isn't finished.

Keep systems understandable

I prefer clear service boundaries and maintainable designs over cleverness. Complexity should earn its place, not arrive by default.

Measure, don't assume

Query plans, real metrics, and production constraints beat intuition about what's "probably" slow. I try to have evidence before I change something for performance.

AI as an accelerator, not a substitute

I use tools like Claude Code, Cursor, ChatGPT, and Gemini, along with MCP-based workflows, to move faster through implementation and exploration. Architecture, trade-offs, and final decisions are still mine — AI speeds up the work, it doesn't replace the judgment behind it.
